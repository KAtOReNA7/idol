# 舞台批量核对：避免反复手工导出

用户已明确要求改善逐步索要备份的流程。本说明覆盖此前“每首都请用户重新下载”的操作惯例，不取消评分保护。

## 当前上线边界

正式v203尚无`idol_stage_owner_preflight`。本地实现待后续获准发布；不为启用此功能自动部署，不冒称目前已经能在线自动取数。CRUSH与Gnarly已采用，不重复核对或导入。

## 新接口上线后的执行顺序

1. 完成候选研究、人工反馈整合、来源身份和版本核验、页面实现与测试。将待采用目标集中成一个既有`idol.stage-evidence.v1`批次；不得先取快照再做长时间开发。
2. 在已连接的私人女团手帐插件中调用`idol_stage_owner_preflight({workIds:[...]})`，一次1–5个精确作品ID。它通过原owner鉴权读取实时状态；不需要用户打开Chrome或下载文件。
3. 将工具的真实`structuredContent`封装原样保存至仓库外临时JSON；不要复制展示过的截断文本，不自行构造内容或更新时间，不将返回内容提交GitHub。无需base64手动解码，导入器负责完整性校验。
4. 立即运行正式工程中的`python scripts/merge-stage-batch.py <已审批次JSON> <仓库外工具响应JSON>`。完整目标集合必须匹配；一次批次最多对应5目标，调用被拒或超时就保留旧来源。过期可重新调用只读工具，不把这个步骤转交用户。
5. 工具拒绝结果过大时拆成更小批次，每批自行重新调用；没有新合格证据就保留待证。若工具尚未部署／插件未更新／授权不可用，明确具体限制，继续不依赖它的工作。备用完整导出仍受原时限保护，但应整批准备后一次核对，不能逐首机械索要。
6. 导入后保存公开采用回执、前后摘要和完整旧来源。私人响应留在本机；GitHub和正式站分别记录。本地采用也不代表已上线。

## 保护边界

- 仅原owner能调用；不引入访问令牌、匿名端点、浏览器会话复制或后台公开读取。
- 0分、有分或任何目标保存日志都不能被当作空槽。工具读取完整日志再过滤目标，不能拿部分分页推断“没有记录”。
- 单次事务读取；源码来源元数据与精确旧binding比较。已审未部署差异仍须按回执独立核验，不能伪造线上前像。
- 替换300秒、新增900秒保持；保护运行在真正导入前，不延长过期文件。
- 封装的SHA只证明字节完整，不证明身份。信任根是实际owner鉴权工具调用，手工编造的封装不是证据。
- 数据库与私人字段写入0；不启动迁移、冻结或修改个人评分。新接口不是通用备份，不替代完整备份用于恢复。
